## 💡 Overview
Git is the industry standard for distributed version control. In enterprise engineering teams, understanding how to manage branches, combine histories cleanly, and resolve code conflicts is essential for maintaining code quality and collaborating effectively across teams.

---

## 🌿 1. Branching Concepts & Command Fundamentals

Branching allows developers to diverge from the main line of development and work independently without affecting production-ready code.

### A. Key Commands
* **Create and Switch to a New Branch:**
  ```bash
  git checkout -b feature/login-auth
  # Or using modern git:
  git switch -c feature/login-auth
  ```
* **List All Local & Remote Branches:**
  ```bash
  git branch -a
  ```
* **Delete a Branch:**
  ```bash
  git branch -d feature/login-auth     # Safe delete (only if merged)
  git branch -D feature/login-auth     # Force delete
  ```

### B. Standard Branching Naming Strategy
In team environments, branches follow clear naming conventions:
* `main` or `master`: Production-ready code.
* `develop` or `staging`: Integration branch for testing upcoming releases.
* `feature/<feature-name>`: Short-lived branches for new individual features.
* `bugfix/<issue-name>` or `hotfix/<issue-name>`: Immediate production fixes.

## 🔀 2. `git merge` vs. `git rebase`

Both commands integrate changes from one branch into another, but they treat commit history differently.

### A. `git merge` (Preserves Exact Chronological History)
`git merge` takes the commits from a feature branch and joins them into the target branch using a dedicated **merge commit**.

```bash
git checkout main
git merge feature/login-auth
```

* **Pros:** Non-destructive. Preserves complete, realistic historical context of when branches were created and joined.
* **Cons:** Can create a cluttered, nonlinear commit graph ("spaghetti history") if many feature branches are constantly merged.

---

### B. `git rebase` (Creates a Linear, Clean History)
`git rebase` takes all commits from your current feature branch and "re-applies" them one by one on top of the latest commit of the target branch.

```bash
git checkout feature/login-auth
git rebase main
```

* **Pros:** Creates a clean, perfectly linear commit history. Eliminates unnecessary merge commits.
* **Cons:** Rewrites commit hashes. **Golden Rule of Rebasing:** *Never rebase shared public branches (like `main`). Only rebase local feature branches before merging.*

---

### Summary Comparison Table

| Feature | `git merge` | `git rebase` |
| :--- | :--- | :--- |
| **History Structure** | Non-linear (creates a merge commit). | Linear (rewrites commits on top of base). |
| **Commit Hashes** | Keeps original commit hashes intact. | Creates brand-new commit hashes. |
| **Primary Use Case** | Merging completed feature branches into `main`. | Updating a local feature branch with the latest `main` changes before submitting a PR. |

## ⚡ 3. Handling Merge Conflicts Step-by-Step

A **merge conflict** occurs when Git cannot automatically determine which changes to keep (e.g., two developers edited the exact same lines in the same file).

### Step-by-Step Conflict Resolution Workflow:

#### Step 1: Identify Conflicting Files
When a merge or rebase fails, Git flags the conflict:
```bash
git status
# Output shows: "Unmerged paths: both modified: src/app.py"
```

#### Step 2: Open and Inspect Conflict Markers
Open the file in your code editor. Git inserts explicit conflict markers:

```python
<<<<<<< HEAD
# Changes on your current branch (e.g., main)
def calculate_discount(price):
    return price * 0.10
=======
# Changes from the incoming branch (e.g., feature/promo)
def calculate_discount(price):
    return price * 0.15
>>>>>>> feature/promo
```

#### Step 3: Resolve the Conflict
Edit the code directly to keep the correct logic, and remove all Git markers (`<<<<<<<`, `=======`, `>>>>>>>`):

```python
def calculate_discount(price):
    return price * 0.15
```

#### Step 4: Stage and Complete
Stage the resolved file and finalize the process:
```bash
# Mark as resolved
git add src/app.py

# If completing a MERGE:
git commit -m "Fix: Resolve merge conflict in discount calculation"

# If completing a REBASE:
git rebase --continue
```

## 🎯 Quick Interview Prep QA

**Q1: When would you choose `git rebase` over `git merge`?**  
> *Answer:* Use `git rebase` on local feature branches to pull in the latest changes from `main` without creating cluttering merge commits, keeping history linear. Use `git merge` when combining a completed feature branch into `main` to preserve the historical record of that branch's lifecycle.

**Q2: What is the Golden Rule of Git Rebase?**  
> *Answer:* Never rebase a branch that has been pushed to a public/shared repository and is being used by other team members. Rebasing rewrites commit hashes, which breaks team synchronization on shared branches.
